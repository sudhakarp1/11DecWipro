10. Rebase vs Merge
	Merge:
		1. Combines both the branches by creating a new merge commit. 
		2. Keeps the history intact(as it is)
		3. History becomes branchy
		
	Rebase:
		1. Rewrite your branch's history by placing your commits on top of another branch 
		2. Create a new clean, lineary history
		3. Does not create a merge commit (unless you have conflicts).
	
		git branch featureOne #checkout
		git rebase main 
	
		When to use rebase:
			you want a clean, linear commit history 
			You are working on your own local branch 
			You want your feature branch to up-to-date before merging
		When to choose merge:
			1.You want to preserve complete history 
			2. You are working in a team
			3. History accuracy matters(like tracking how brances diverged).
			4. You are merging shared branches

11. Forking and Cloning
-----------------------
	git clone repositoryURL 
		this is used to download a full copy of a repository (including its history) to your local machine.
	
	When you clone:
		you get your own local working copy 
		you can commit locally 
		your are connected to the original repo as origin/master
	Clone is used when:
		You have permission to push directly 
		you are working within the same project/team 
		That means you are not modifying some one else's open-source project.
		
====================================
	A fork is your own server-side copy of some one else's repository. usually on GitHub/GitLab/Bitbucket
	
	When you fork:
		you create your own copy on GitHub. 
		You can push freely to your fork not the original. 
		You have to open Pull requests to propose changes to the original repo 
	
	Fork is used when:
		you are contributing/writing to open-source projects
		You do not have write permission to the original repo.
		You want an separate copy for experimentation.
		
What is a Pull-Request(PR)?
	A pull-request is a request to merge your fork(Branch) into the main(Branch).
	When is it used:
		1. Collaborate (Contribute into the project)
		2. Your code to be reviewed by your Peers.
		3. Discuss changes 
		4. Ensuring your code has quality before merging 
		5. Keeping the history clean.
	
	When do you create a Pull-Request (PR)?
		1. When you have completed work on a feature(Branch)
		2. The changes has been reviewed
	
	Steps involved:
		1. Create a feature branch 
		2. Make changes by adding and commit 
		3. Push to your remote repo 
		
	CI/CD Checks:
		1. Must pass test cases 
		3. Your code has to follow the coding guidelines along with stye.
		i.e., if something fails, fix --> push --> rerun checks.
		
Example of GitHub PR Workflow:
------------------------------
	Developer --> Creates feature branch --> Push --> Opens PR
        ↓
	Reviewers --> Comment --> Request changes --> Approve
        ↓
	CI/CD --> Run tests --> Lint --> Build --> Security scan
        ↓
	Merge --> Squash --> Delete branch --> PR closed
